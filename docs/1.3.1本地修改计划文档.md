## 1. 目标与执行边界

本版本的目标是把 Cocos 1.3/1.3.1 已确认的规则与体验改动，按 Godot 当前工程结构完成本地对齐；不复制 Cocos 的 TypeScript 文件名、微信构建脚本或其关卡编号。

实施以 Godot 的实际主线结构为准：第一章目前为 `stage_1_1` 至 `stage_1_5`，其中 `stage_1_5` 是 Boss。涉及首通道具时，按“新手捕捉引导关 / 第一章 Boss”这一语义映射，不直接照搬另一工程的关卡序号。

除非本计划另有明确说明，既有主线、共鸣塔、信箱领奖、捕捉、牧场和存档兼容链路不得回退。所有存档字段新增或语义变更必须能读取旧档，并至少覆盖一次升级后的保存与重载。

## 3. 已有能力：不重复开发

以下能力已在 Godot 当前源码中存在，是 1.3.1 的回归前提，而不是新的施工项。

1. `SaveManager.reset_to_initial_state()` 已生成三只 `MonsterPool.DEFAULT_STARTERS`、初始等级 6、完整三人队、金币/钻石为 0、体力 5/5、空背包和三颗初始图鉴星星。
2. `SaveManager` 已定义 `STAMINA_MAX = 5`、6 小时恢复 1 点，并只在 `do_sweep()` 中消耗 1 点；普通进入战斗不扣体力。
3. `SaveManager.add_monster_instance()` 已在首次获得物种时调用 `MailboxRules.award_new_species_star()`；重复获取不会重复加星。
4. `ResultLogic.build_captured_instance_options()` 已使用捕捉目标的 `level`，不会从星级或固定值派生捕捉等级。
5. `RewardRules.calc_sweep_rewards()` 已只返回金币/经验并按 80% 结算；`StageDB` 已有主线经验 1.3 倍率与 Boss 额外倍率。
6. 选关地图已有 `MAP_SCROLL_DRAG_THRESHOLD`、本次拖动抑制和延迟清除逻辑；课堂精灵卡已有“已出战”标记；农场和社交对象互斥已有存档层保护。

## 4. P0：规则、存档与战斗正确性

### P0-0 初始性格与首发社交

**现状。** 初始精灵的种类和等级已固定，但 `reset_to_initial_state()` 调用 `MonsterPool.create_instance()` 时未传入性格；`create_instance()` 会使用 `NatureDB.random_nature()`。新档三只精灵因此可能得到重复性格，不能保证首次社交具有稳定、可感知的差异。

**改动。**

1. 在 `MonsterPool` 或与其相邻的启动数据处定义三个有效且互不重复的初始性格，按 `DEFAULT_STARTERS` 的物种 ID 显式映射；不得依赖随机种子。
2. `reset_to_initial_state()` 创建初始实例时传入对应性格；旧存档不强制改写已拥有精灵的性格。
3. 用固定的新档和两只初始精灵跑一次社交结算，断言结果包含有效的性格/社交变化提示；不把“必然产生同一种数值结果”写死为跨版本契约。

**验收。** 连续重置三次，新档三只精灵的性格组合完全相同且互不重复；任意两只初始精灵可进入首次社交并得到可见结果。

### P0-1 主线首通奖励统一

**现状。** `src/ui/controllers/result_logic.gd` 在 `_calc_rewards()` 中无论是否首通都会读取 `RewardRules.get_first_guaranteed_item()`；非首通胜利还有 30% 随机道具掉落。这与“常规关只结算金币/经验，道具与钻石只在首通发放”的 1.3.1 口径不一致。

**改动。**

1. 先计算并锁定 `first_clear`，再决定首通钻石和首通道具；非首通不得进入 `guaranteedItems` 与随机掉落分支。
2. 继续仅使用奖励表的第一个 `guaranteedItems` 条目；扫荡仍不得携带道具或首通钻石。
3. 在 `src/data/stage_db.gd` 复核第一章的引导道具配置：Godot 当前只在 `stage_1_2` 配置首通捕捉球，而 Cocos 记录列出两个早期关卡各给一枚。先由产品确认 Godot 是否也需要增加第二枚；未确认前保持“明确捕捉教学关给球、第一章 Boss 给高级捕捉球”的语义，不按另一工程关卡编号机械复制。若产品确定“初始捕捉球也完全取消”，也应作为独立数值决策。
4. 保持普通首通 3 钻、Boss 首通 10 钻，且奖励落库仍通过既有收据/事务路径。

**涉及文件。** `src/ui/controllers/result_logic.gd`、`src/battle/reward_rules.gd`、`src/data/stage_db.gd`、相关奖励测试。

**验收。** 同一关连续胜利两次：第二次只有金币、经验和共享精灵经验；扫荡只有 80% 金币/经验；首通道具、钻石和奖励收据均不重复。

### P0-2 远行信箱：稳定伪随机分批投递

**现状。** `MailboxService.send_blessing()` 在送出祝福时立即创建并写入 `inbox`，且使用当前时间作为 seed；重新打开不改奖励，但不具备延时批次投递。

**目标规则。**

1. 每个自然日生成 1–6 个投递批次，时间落在当天 09:00 之后的 12 小时窗口内。
2. 同一天、同一存档规则下批次时间稳定；反复进入游戏、读取信箱不能重掷时间或奖励。
3. 送祝福后进入下一个未来批次；当天没有未来批次时排到次日第一个批次。
4. 到期前不显示为收件箱未读邮件；读取信箱或返回大厅前的刷新会把到期 `pending` 邮件转入 `inbox`，并只触发一次到达表现。
5. 保留现有每天送祝福上限 3 次，除非后续产品文档另行调整。

**存档与接口设计。**

1. 将 `SAVE_SCHEMA_VERSION` 递增；在 `mailbox` 状态中新增 `delivery_schedule`（按日期保存批次）与 `pending_blessings`（已渲染邮件快照、`deliver_at`、稳定 `seed`、收据 ID）。旧档默认空队列并可正常读取。
2. 在 `MailboxRules` 集中处理日期键、日程生成、下一个批次选择和 pending 标准化；不得把随机和时间规则散落在 UI。
3. `BlessingProvider` 根据持久化 seed 生成模板及附件；`MailboxService` 负责排队和将到期项一次性物化到收件箱。物化过程必须幂等、受邮箱容量规则保护。
4. `scene_mailbox.gd` 与 `scene_main.gd` 读取状态前调用统一刷新入口，确保邮件到期后可见、未读红点和到达动画一致。

**邮件内容扩展。** 在 `mail_content_db.gd` 增加更完整的旅途文案池及固定组合包；允许金币、共享经验、药水、捕捉球、锤子等低价值组合，禁止直接投放钻石和高级进化石。排队后邮件正文与附件均不可因重开游戏变化。

**验收。** 使用可注入时钟/日期的测试覆盖：日程稳定、跨日、无未来批次、多个待投递项、到期物化幂等、附件不重掷、红点/到达表现只播放一次、领取事务失败回滚。

### P0-3 队长技改为独立五点蓄能队列

**现状。** `BattleManager` 已按精灵记录 `leader_charge_points`，但 `is_leader_burst_ready()` 调用 `_all_leader_charges_ready()`，`consume_ready_leader_burst()` 只释放当前活动队长并清空全队蓄能。这与 1.3.1 的单体独立蓄能不一致。

**改动。**

1. 每只存活且拥有队长技的精灵独立拥有 0–5 点蓄能；其自身达到 5 点即可入队，不再等待全队。
2. 新增持久于战局内的 ready queue，以“本次填满的先后顺序”为唯一顺序；同一轮级联内多只充满时按事件生成顺序入队且不重复入队。
3. 每次释放只执行队首精灵的队长技，并只清空该精灵的蓄能；死亡、无技能、目标已清空的单位须安全跳过。
4. 队长技表现不得截断棋盘 combo。棋盘继续结算时可继续向队列添加任务；敌方回合和战斗结束前统一处理队列与死亡过滤，战斗结束后不得再执行后续敌方回合。
5. `leader_charge_events` 增加 `cascade_index`；在每段级联结算时立即更新 UI，而不是只在整段 combo 尾部刷新。

**涉及文件。** `src/battle/battle_manager.gd`、`src/ui/scene/scene_battle.gd`、`src/ui/scene/scene_battle_gui.gd`、`src/ui/components/battle_leader_charge_point.gd`，以及队长技执行/表现测试。

**验收。** 三只精灵的蓄能可独立从 0 到 5；任意一只满点立即排队；同级联多次满点按序释放；释放 A 后 B 的蓄能不丢失；combo、转火、阵亡单位与击杀收尾均正确。

### P0-4 首次有效消除专项回归

当前 `scene_battle.gd` 已在每个消除段调用 `process_match_result()`，而 `BattleManager.process_match_result()` 会结算伤害、命中日志和蓄能。该项先不重写现有流程。

新增一条确定棋盘的运行/逻辑用例，断言进入战局后的第一次有效交换同时产生：玩家伤害、命中反馈事件、蓄能事件及正确目标选择。若用例复现失败，再以最小改动修复交换接受到首段消除结算之间的时序，不得用延迟或重复结算掩盖问题。

## 6. P2：平台显示与资源审计

### P2-1 全面屏与安全区

Cocos 的 `MATCH3_FULL_SCREEN_CANVAS_PATCH`、`showStatusBar=false` 与 `ditu.png` 顶底草地遮挡是微信小游戏构建方案，不能直接迁入 Godot。

先在 Godot 的目标导出平台进行 16:9、刘海屏和全面屏截图验收：检查是否出现上下黑边、内容被安全区遮住、或背景未覆盖真实窗口。仅当问题复现时再实施以下 Godot 适配：

1. 使用 Godot 显示/拉伸设置与运行时安全区 API 计算内容区；不要硬编码微信设备尺寸。
2. 如需装饰遮挡，新增独立 `SystemChromeOverlay.tscn`，置于场景根的最高 `CanvasLayer`，顶部与底部图层使用可替换、可镜像的正式资源。
3. 覆盖层不得截断按钮、吞掉输入或影响 375×667 基准截图；仅覆盖系统留白区域。

### P2-2 资源与包体

1. 检查新增资源是否放入正确的 `assets/images/<page>_new/` 或既有正式目录，避免使用概念图、截图或无引用临时资产。
2. 对导出包执行尺寸审计；新常驻背景和动效资源先压缩/缩放，再加入启动场景。
3. 运行正式资源引用、场景资源和截图质量测试；如项目新增移动端/微信导出链路，再另建该平台的包体与配置审计，不沿用 Cocos 脚本名称。
