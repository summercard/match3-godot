## 1. 施工原则

1. 共鸣塔与远行信箱分为两个独立领域；“塔奖励通过邮件投递”是唯一业务连接。
2. 不把塔楼层写入主线 `StageDB`，不使用主线星级、首通或扫荡逻辑。
3. 不把邮件奖励直接写进背包；所有附件通过带收据的领取事务发放。
4. 所有新页面使用正式 `.tscn` 场景接入 `main.gd` 的 `PACKED_SCENE_MAP`，不使用概念图直裁或运行时临时页面。
5. 每一个塔进度、卡牌选择、邮件领取与送祝福事件都必须可持久化、可恢复、可重复调用而不重复结算。

## 2. P0 前置条件闭环

2026-07-13 已恢复既有商店、关卡地图等场景资源引用，并完成 P0 与全量回归；当前结果为 **123 / 123 通过**。本节保留的约束是：任何后续修改仍须先保证既有页面资源可加载，再改变共鸣塔或信箱页面，避免以新增功能掩盖旧链路的资源问题。

施工期间不得覆盖当前工作区中已有的 `project.godot`、审核资产 `.import` 文件和 `exports/` 未跟踪内容。

## 3. 共鸣塔技术方案

### 3.0 成品级页面包装

- 正式场景仍使用 `src/ui/scenes/tower.tscn`；背景资源固定放在 `assets/images/tower_new/`，以可替换的 `TextureRect + Shade + Panel` 分层承载，禁止将概念图或临时截图嵌入界面。
- 页面视觉以“晴空共鸣塔、蓝紫晶体、金色远征按钮”为主题；层数、五波节点、榜单与按钮使用浅色半透明阅读卡，保证背景可见且中文信息可读。
- 解锁规则仍为 `stage_1_8` 通关。测试环境通过存档标记该关三星通关，不修改线上规则或默认新玩家状态。

### 3.0.1 轻松向美术与失败奖励补充

- 塔主页改为明亮的水晶山坡与晴空手绘背景；塔内战斗使用独立的“水晶庭院”场景，不复用主线关卡地图。敌方精灵在塔内以各自基础体型再放大 30%。
- Boss 卡牌、失败页与补给卡统一使用轻量的蓝金色纸卡、圆润按钮和短促入场动效；不使用常驻粒子雨或高频全屏特效。
- 全队倒下或回合耗尽时，以安全点为单位首次送出一份“旅行精灵鼓励”到远行信箱，包含少量金币与共享经验；相同安全点不会重复发放。失败不提高登塔层数，单回合爆发纪录照常保留。

### 3.1 新模块

| 模块 | 建议路径 | 职责 |
|---|---|---|
| 塔配置 | `src/data/tower_db.gd` | 99 层分段、敌人组合、地图主题、Boss、奖励和解锁条件 |
| 塔规则 | `src/core/tower_rules.gd` | 层级生成、卡牌候选、叠层限制、安全点、排名口径 |
| 塔运行控制 | `src/core/tower_run_controller.gd` | 当前波次推进、队伍状态继承、失败回退、存档快照 |
| 塔排行榜提供方 | `src/core/tower_rank_provider.gd` | 本地个人记录与模拟旅行者榜；后续真实平台替换实现 |
| 塔界面 | `src/ui/scenes/tower.tscn` + 控制器 | 入口、五波地图标签、卡牌选择、榜单与继续远征 |

`TowerDB` 应按阶段模板生成大部分层数，而不是手写 99 份近似配置。第 5、10、…、95 与第 99 层使用显式 Boss 配置；地图和敌人生态按阶段替换。

### 3.2 塔运行状态

在 `SaveManager` 中新增独立 `tower` 段，并将存档 schema 升级。建议状态：

```gdscript
{
  "season_id": "tower_s1",
  "unlocked": false,
  "current_floor": 1,
  "current_wave": 1,
  "checkpoint_floor": 1,
  "party_instance_ids": [],
  "party_snapshot": [],
  "board_snapshot": {},
  "buffs": [],
  "supplies": [],
  "stage_seed": 0,
  "checkpoint_snapshot": {},
  "highest_floor": 0,
  "total_player_turns": 0,
  "highest_turn_damage": 0,
  "claimed_stage_rewards": []
}
```

- `party_snapshot` 保存实际 HP、护盾、技能充能和状态；不能只保存怪物 ID。
- 每波胜利后保存可恢复状态；每个 Boss 后写入安全点快照。
- 失败时恢复 `checkpoint_snapshot`，阶段奖励领取状态不回滚。
- `board_snapshot` 首版可先保留棋盘种子和必要状态；如确认跨波完整保留棋盘，再扩展为完整棋盘序列化。

### 3.3 战斗链路改造

现有 `BattleManager.check_battle_end()` 在敌人清空时直接结束战斗，`SceneResult` 随后发放主线奖励。共鸣塔必须在同一战斗场景内截获这个节点：

1. 小怪波清空：`TowerRunController` 保存我方状态，替换为下一波敌人，刷新敌方目标，不释放当前场景。
2. Boss 波清空：保存阶段安全点，生成阶段奖励邮件，打开三选一卡牌覆盖层。
3. 全队倒下或回合耗尽：打开“远征受挫”覆盖层；先保存本次最高单回合伤害，再将队伍状态、充能与护盾恢复到安全点。失败不抬升登塔层数，玩家可选择从安全点再战或返回共鸣塔。
4. 卡牌选择确认：写入塔 Buff/塔内道具，加载下一阶段地图或继续当前塔进度。
5. 第 99 层胜利：写入最高层和赛季完成状态，进入塔专属总结页。

`BattleManager` 需要新增塔模式上下文，例如 `mode=tower`、`tower_floor`、`tower_buffs`、`disable_capture=true`。塔模式禁止捕捉与主线星级保存；`result_logic.gd` 必须按模式分流，不能调用 `save_stage_stars()`。

### 3.4 单回合伤害

当前战斗结果只暴露各精灵总伤害。新增统计字段：

```gdscript
{
  "current_player_turn_damage": 0,
  "highest_player_turn_damage": 0
}
```

- 在有效换位开始时清零本回合伤害。
- 消除、连锁、特殊宝石和该回合触发技能统一累加。
- 敌方 DOT、延迟状态、反射等不计入爆发榜。
- 每次突破个人最高记录时立刻保存塔记录，并向排行提供方提交。

### 3.5 随机与公平接口

- 卡牌候选由 `season_id + floor + checkpoint` 生成固定种子，同期玩家面对同层时拿到同一组三选一候选。
- 敌人和地图压力由同一种子配置。
- 当前棋盘、伤害、敌方目标仍存在全局随机调用。1.2 模拟榜可先使用本地记录；接真实排行榜前，必须把塔模式改为可注入、可复算的随机源。
- 排名数据接口先实现 `MockTowerRankProvider`；不在 UI 层伪造网络实现。

### 3.6 塔奖励投递

- 每个 Boss 阶段生成一个固定奖励包，调用邮箱服务创建“共鸣塔阶段补给”邮件。
- 邮件 ID 建议为 `tower_reward:<season_id>:<boss_floor>`。
- 领取附件复用 `SaveManager.run_transaction()` 与奖励收据；同一 Boss 奖励只能领取一次。
- 卡牌选择是塔内状态，不能作为邮件附件延迟选择。

## 4. 远行信箱技术方案

### 4.0 成品级页面包装

- 正式场景仍使用 `src/ui/scenes/mailbox.tscn`；背景资源固定放在 `assets/images/mailbox_new/`，以“远方小镇、星光信箱、飞行祝福”为视觉主题。
- 祝福页必须展示当前派遣精灵肖像、名称和等级；切换精灵、送出祝福、飞星、未读红点与附件领取均保留正式按钮反馈。
- 收件箱与祝福页使用同一套奶油白阅读卡、金色标题和蓝色选中态，背景插画只作氛围层，不降低邮件正文和奖励信息的可读性。

### 4.0.1 轻松向美术补充

- 信箱页改为晴天小镇与蓝金色信箱背景，采用奶油白阅读卡与天蓝色页签；收件详情保留高对比正文和附件按钮。
- 送祝福仅使用一颗旋转飞星作为反馈，并保留按钮按压回弹；不增加持续粒子或复杂的镜头特效。

### 4.1 新模块

| 模块 | 建议路径 | 职责 |
|---|---|---|
| 邮件内容 | `src/data/mail_content_db.gd` | 陌生人祝福、系统奖励、标题、文案、附件权重 |
| 邮箱规则 | `src/core/mailbox_rules.gd` | 每日次数、随机结果、邮件容量、过期与未读数 |
| 邮箱服务 | `src/core/mailbox_service.gd` | 创建、阅读、领取、送出祝福与塔奖励投递 |
| 祝福提供方 | `src/core/blessing_provider.gd` | 初版模拟陌生人；未来替换真实社交服务 |
| 邮箱界面 | `src/ui/scenes/mailbox.tscn` + 控制器 | 选择精灵、送出动画、收件箱、红点状态 |

### 4.2 邮件状态

在 `SaveManager` 中新增独立 `mailbox` 段：

```gdscript
{
  "selected_adventurer_id": "",
  "daily_send_count": 0,
  "daily_reset_at": 0,
  "inbox": [],
  "sent_history": [],
  "unread_count": 0
}
```

每封邮件必须保存渲染后的内容快照，而不是每次打开时重新随机：

```gdscript
{
  "id": "mail:...",
  "source": "stranger_blessing|tower_reward|system",
  "sender_name": "远方的冒险者",
  "title": "一份温暖的祝福",
  "body": "...",
  "attachments": [],
  "created_at": 0,
  "read_at": null,
  "claimed_at": null,
  "reward_receipt_id": "mail_reward:..."
}
```

### 4.3 送祝福流程

1. 选择已拥有精灵并保存 `selected_adventurer_id`。
2. 点击“送出祝福”后立即锁定按钮，播放精灵发光和星星飞向远方的动画。
3. 动画完成后调用 `BlessingProvider.send()`，写入发送历史和当天次数。
4. 首版由模拟提供方按配置生成未来的陌生人祝福邮件；玩家可见文案明确为陌生冒险者，不宣称是真实玩家。
5. 成功、次数已用尽、存档失败均要有明确反馈，不能出现动画完成但状态未保存。

### 4.4 奖励安全

- 每日发送次数、入站邮件数、附件权重和邮箱容量全部放入配置。
- 陌生人祝福只投放轻量资源；高价值奖励只能来自明确的系统邮件与固定里程碑。
- 领取邮件走事务和收据；删除、过期或重复点击都不能造成丢奖或重复奖。
- 塔奖励邮件不受陌生人祝福次数限制。

## 5. 场景与入口施工

1. 在 `main.gd` 的 `PACKED_SCENE_MAP` 中注册 `tower` 与 `mailbox`。
2. 大厅新增 `TowerButton` 与 `MailboxButton`；邮箱按钮显示未读红点，塔按钮显示解锁条件或最高层。
3. `tower.tscn` 中包含同阶段五波路线标签、继续/退出、排行榜入口和卡牌覆盖层。
4. `mailbox.tscn` 中包含精灵选择区、送祝福按钮、飞星动画层、收件列表和附件领取按钮。
5. 所有可点击控件接入统一按压/释放反馈；新增美术放在正式 `assets/images/<page>_new/` 目录，不能引用概念图目录或旧页面资源填充。
